# Подписки — задачи №38 и №43

## Реализовано

- `/subscriptions` использует существующие Sidebar, Header и защиту маршрута.
- `SubscriptionsPage` размещает фильтры, таблицу и ссылку «Добавить подписку» на `/subscriptions/new`.
- `SubscriptionsTable`: название, цена за месяц, категория, дата списания, действия, активность.
- Skeleton, «Подписок нет», «Ничего не найдено», ошибка и повторная загрузка.
- Компонент `Filters`: поиск по названию, категория и период работают совместно. Поиск игнорирует регистр и пробелы по краям; сброс очищает все поля.
- Таблица прокручивается горизонтально на узком экране, фильтры перестраиваются.
- Деньги хранятся в копейках; дата отображается без сдвига часового пояса.

## Проверка без backend

Запустите `npm run dev` из `frontend`. На странице входа нажмите существующую кнопку демо-входа и откройте «Подписки».
Демо доступно только в режиме разработки; тестовые данные явно обозначены.
Переключатели позволяют проверить данные, пустой список, Skeleton и ошибку.
Неавторизованный посетитель переходит на `/login`.
Для обычного аккаунта показывается сообщение о недоступной интеграции, а не вымышленные подписки.

Добавлены формы создания/редактирования Полины и окно удаления — задачи №39, №50 и №51. Это предпросмотр UI: кнопки сообщают, что данные не сохранены/не удалены до подключения API. Сохранение даже демо-записей пока не реализовано. Результаты ревью и ограничения описаны в FORMS-REVIEW.md.
Статус активности отображается как текст, не меняется на сервере.

## Подготовка API — ещё не реальная интеграция

Backend списка пока отсутствует. `createSubscriptionsApi().list()` подготовлен для GET `<VITE_API_BASE_URL>/subscriptions`;
по умолчанию это `/api/subscriptions`, запрос передаёт Bearer-токен существующей сессии.
Префикс необходимо согласовать со Swagger. Таймаут — 10 секунд; при уходе со страницы запрос отменяется.
401 завершает сессию, другие ошибки показываются с возможностью повторить загрузку.

Адаптер сейчас ожидает JSON-массив **внутренней модели frontend**, а не утверждённый контракт backend:

```json
[
  {
    "id": "1",
    "name": "Кинопоиск",
    "monthlyPriceMinor": 29900,
    "currency": "RUB",
    "category": "Кино",
    "period": "monthly",
    "nextPaymentDate": "2026-10-15",
    "active": true
  }
]
```

`monthlyPriceMinor` — месячный эквивалент в копейках, включая годовые подписки. Формулу округления должен подтвердить backend/аналитик.
Сейчас поддержаны RUB, месячный и годовой периоды. Дополнительные валюты и периоды добавляются после согласования требований.
Когда появится API, адаптируйте ответ в `subscriptions/api.ts` к этой модели и только затем включите
`VITE_SUBSCRIPTIONS_API_ENABLED=true` в локальном frontend env (перезапустите Vite; для Docker пересоберите frontend).
Секреты и `.env` не коммитить. По умолчанию реальные запросы выключены.

В демо фильтры локальные. В подготовленном API-режиме фильтры передаются серверу, а не применяются повторно к ответу:
`GET /api/subscriptions?search=...&category=...&period=monthly`.
Пустые параметры не передаются; значения кодируются через `URLSearchParams`. Названия `search`, `category`, `period` пока предложены frontend и НЕ согласованы с backend.
Смена фильтров отправляет запрос после паузы 300 мс; предыдущий запрос отменяется и не может перезаписать новый результат.
Во время серверной загрузки поля остаются доступными, при смене демо-сценария фильтры сбрасываются.
Категории в API-режиме пока накапливаются из полученных списков и сохраняются при фильтрации, чтобы варианты не исчезали.
После готовности словаря №41 замените этот источник полным справочником, особенно при пагинации.
Query-параметры, значения периодов, идентификаторы категорий и пагинация требуют согласования с backend в задаче №44.
Не используйте фильтрацию одной страницы ответа как фильтрацию всего списка. Пока `VITE_SUBSCRIPTIONS_API_ENABLED` выключен, реальные запросы не отправляются.
